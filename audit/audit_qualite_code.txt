--- 1. OUTILLAGE STATIQUE ---

[1.1 Linter] Aucun linter configuré
- Constat : pas de .eslintrc / eslint.config.*, ni de biome.json. ESLint n'est pas dans les devDependencies et `package.json` n'a pas de script `lint`.
- Preuve : `ls -la` à la racine. `ls node_modules/.bin` liste seulement baseline-browser-mapping, jiti, nanoid, next et semver. package.json ne contient que dev/build/start/format.
- Criticité : Haute — Effort : Petit
- Recommandation : `npm i -D eslint eslint-config-next`, ajouter un `eslint.config.mjs` (preset next/core-web-vitals) et un script `"lint": "eslint ."`. Les règles no-unused-vars et react-hooks/exhaustive-deps feraient immédiatement remonter plusieurs findings de la section 5.

[1.2 Formatter] Prettier invoqué mais ni configuré ni installé
- Constat : le script `"format": "npx prettier . --write"` télécharge une version non figée de Prettier. Il n'y a pas de .prettierrc ni de script de vérification. Dans les faits, le code n'est pas formaté de façon homogène : guillemets simples dans layout.js, footer.jsx et page.jsx contre doubles dans navbar et arrowUp, points-virgules présents ou absents selon les fichiers, indentation cassée (layout.js:145-160, footer.jsx:9-84, notre-expertise:52-65).
- Preuve : package.json et lecture des fichiers cités.
- Criticité : Moyenne — Effort : Petit
- Recommandation : `npm i -D prettier prettier-plugin-tailwindcss`, créer un `.prettierrc`, ajouter `"format:check": "prettier . --check"` et faire un commit de formatage global isolé.

[1.3 EditorConfig] Absent — Criticité : Basse — Effort : Petit. Ajouter un `.editorconfig` (utf-8, lf, indentation 2 espaces, trim_trailing_whitespace).

[1.4 Pre-commit hooks] Absents. Pas de husky, lefthook ou lint-staged, et aucun dossier `.github/` (donc pas de CI).
- Criticité : Moyenne — Effort : Petit. Ajouter husky et lint-staged (eslint --fix et prettier --write sur les fichiers indexés). La CI relève de la skill CI/CD.

--- 4. ARCHITECTURE ET DESIGN ---

[4.1 / 4.2 Couches] Root layout transformé en composant client portant une logique applicative
- Constat : app/layout.js est `'use client'` (ligne 1) et mélange polices, portail d'accès (useState et sessionStorage) et structure HTML. - Preuve : layout.js:1, 15, 109-181.
- Criticité : Haute — Effort : Petit
- Recommandation : rendre le layout serveur (retirer `'use client'`), réactiver `export const metadata` et le JSON-LD, et déplacer le portail dans un composant client `<AccessGate>` (ou le supprimer si le site est public). Un seul `<html>`.

[4.1 KISS / React] Manipulation directe du DOM au lieu de l'état React
- Constat : page.jsx:30-35 utilise `document.querySelector` puis `classList.remove`. notre-expertise:49-56 fait `classList.toggle("scale-110")` alors que la même classe est aussi pilotée par l'état `activeCard` (lignes 83-84), ce qui crée un conflit potentiel entre deux sources de vérité. nos-realisations:11-12 utilise `getElementById`. arrowUp:9 dépend d'une classe CSS globale `.not-arrow-up` posée à la fois dans navbar et page.jsx, un couplage implicite.
- Criticité : Moyenne — Effort : Petit
- Recommandation : utiliser `useRef` et l'état React pour les classes, et passer une ref explicite (ou un id dédié) à ArrowUp.

[4.3 Couplage] Usage excessif de `'use client'` : 8 fichiers sur 11, dont les pages entières page.jsx et nos-realisations pour quelques animations. Footer est client uniquement pour `usePathname`. Criticité : Basse ici. Extraire de petites îles client. L'impact sur les performances relève de la skill Performance.

[4.4 Effets de bord] Effets limités et nettoyés (observers déconnectés, timers clear), sauf le `setTimeout` de page.jsx:33 qui n'est pas nettoyé au démontage. Criticité : Basse.

[4.5 Anti-patterns] `<a href>` utilisé pour la navigation interne à la place de `next/link` dans navbar et footer (Link n'est utilisé que pour « Contact »). Le comportement est incohérent : chaque clic recharge toute la page, et la navbar mobile ferme son menu à la main. Criticité : Basse — Effort : Petit.
